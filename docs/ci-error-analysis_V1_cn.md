# CI 失败归因服务

> 面向 Studio 的可复用 CI 失败分析能力：当 Jenkins 或蓝盾构建失败时，服务先拉取构建日志交给 Agent 分析，只有在日志证据指向源码问题时，才去读取 Git / Perforce 的源码上下文。

## 概述

CI 失败归因服务把 CI 失败分诊中反复出现的一个 Agent 循环产品化：

1. CI 系统发送构建失败 Webhook。
2. 服务校验、规范化失败构建事件并写入队列。
3. Agent 从 CI 服务器拉取构建日志与构建元数据。
4. Agent 先分析构建日志，定位主要失败原因。
5. 只有当日志证据指向源码问题时，Agent 才读取相关的 Git / Perforce 上下文，例如提交、changelist、文件或 blame。
6. 服务生成一份精简的根因报告，并发送到可插拔的通知出口，例如企业微信、Slack 或其他团队工作流。

它被设计成一项可复用的 Studios 能力。它不是一次性流水线脚本，而是一套可重复的模式：失败事件接入 → Agent 分析 → 由证据把门的上下文检索 → 通知。

## 为什么需要

CI 失败分诊存在反复出现的运维成本：

- 失败证据分散在 Jenkins / 蓝盾、原始构建日志、源码变更与团队聊天里。
- 工程师反复打开构建链接、扫日志、找失败步骤，并判断这次失败是否与代码有关。
- 常见错误与项目专属知识混在一起，经验难以复用。
- 多个 Studio 需要相似的 CI/SCM/通知集成，却往往各自重复建设。

CI 失败归因服务把这些工作变成一个稳定的循环：接收事件、收集有边界的证据、运行 Agent 分析、把简短可执行的报告送回团队工作流。

## 核心循环

```text
构建失败 webhook
  -> 规范化失败事件
  -> 分析任务入队
  -> 从 CI 服务器拉取构建日志
  -> 用 Agent 分析构建日志
  -> 当日志证据指向源码问题时，可选地拉取源码上下文
  -> 生成根因报告
  -> 通知已配置的出口
```

设计原则：

- **日志优先**：先分析原始 CI 日志，再碰源码仓库。
- **源码访问由证据把门**：只有当日志里出现堆栈、文件路径、编译错误、测试失败、提交或 changelist 等证据时，才读取源码上下文。
- **上下文只读**：访问 SCM 只用于收集证据；服务不会修改代码。
- **报告要短**：通知应简短、可执行、可追溯。
- **投递可插拔**：报告可以通过团队惯用的出口投递，例如企业微信、Slack 或未来的集成。

## 架构

![CI 失败归因服务 —— 高层架构](assets/images/ci-error-analysis-high-level.jpg)

主要组件：

| 组件 | 角色 |
| --- | --- |
| CI 系统 | Jenkins / 蓝盾的构建失败事件源 |
| Webhook API | 接收构建失败 Webhook，解析各平台的 payload 并规范化事件 |
| 入站事件队列 | 存放待分析的失败事件，带去重、重试与异步处理 |
| 分析工作器 | 拉取构建日志并运行基于 Agent 的失败分析 |
| 源码仓库 | Git / Perforce 源码上下文，仅在需要时使用 |
| 出站通知队列 | 存放待投递的报告，使分析与通知解耦 |
| 通知工作器 | 通过可插拔的通知出口（企业微信、Slack 或未来集成）发送报告 |

## 运行时流程

![CI 失败归因服务 —— 运行时流程](assets/images/ci-error-analysis-flow.jpg)

流程：

1. **CI 服务器 → 归因服务**  
   Jenkins / 蓝盾发送构建失败 Webhook，携带 build id、job / pipeline、构建 URL、分支、提交及相关元数据。

2. **校验并入队**  
   服务校验失败事件、规范化字段、对重复投递去重，并把任务写入入站队列。

3. **从 CI 服务器拉取构建日志**  
   Agent 依据平台配置与构建元数据，拉取控制台日志、失败步骤与构建上下文。

4. **用 Agent 分析构建日志**  
   Agent 先从日志给失败分类：环境问题、依赖问题、编译错误、测试失败、工具链问题、资源问题或其他类别。

5. **只在必要时拉取源码**  
   如果日志证据指向源码问题——例如源文件、堆栈帧、编译错误、测试断言、提交或 changelist——Agent 才读取相关的 Git / Perforce 上下文。

6. **生成并投递报告**  
   服务生成一份精简的根因报告，并通过已配置的通知出口发送。

## Agent 应该报告什么

建议的报告结构：

```text
结论：<一句话给出最可能的根因>

证据：
- <日志中的关键错误>
- <失败步骤 / job / 构建链接>
- <可选：相关的提交 / changelist / 文件证据>

建议：
- <下一步调试或修复动作>

归属信号：
- 触发用户：<构建触发者>
- 候选变更作者：<仅在有 SCM 证据支持时给出>
```

应当避免：

- 在没有源码证据的情况下把责任推给某个变更作者。
- 贴大段日志却不给结论。
- 过早地读取整个仓库或同步大型 Perforce 工作区。
- 在报告里包含密钥、token、webhook key 或凭据。

## 能力契约

| 领域 | 契约 |
| --- | --- |
| 输入 | Jenkins / 蓝盾构建失败 Webhook |
| 输出 | 面向已配置团队工作流的精简根因报告 |
| CI 访问 | 只拉取当前失败构建的日志与元数据 |
| SCM 访问 | 默认关闭；开启后也只在日志证据要求时读取源码上下文 |
| 通知 | 面向企业微信、Slack 或未来渠道的可插拔出口模型 |
| SCM 集成 | 通过灵活的 Agent skill 与只读证据收集，支持 Git、Perforce 等现代 SCM 系统 |
| 状态 | SQLite 入站 / 出站队列，带去重、重试与留存清理 |
| 安全 | Agent 策略应保持 CI 与 SCM 检查为只读 |

## 集成接口

### Jenkins

对 Jenkins Pipeline 与 multibranch Pipeline 任务，推荐的集成方式是共享库。Jenkinsfile 只需要一个失败后的 post 钩子：

```groovy
post {
  failure {
    ciErrorAnalysisNotify()
  }
}
```

对 freestyle 任务，可改用 Jenkins Notification 插件。

### 蓝盾 BK-CI

蓝盾发送构建结束事件。服务只接受失败的构建：

```text
event = BUILD_END
data.status = FAILED
```

### 可插拔的通知出口

分析结果通过一层出口抽象投递，而不是绑死在某个聊天系统上。目前支持企业微信，同样的模式也可以支撑 Slack 或其他 Studio 内部工作流。

### 现代 SCM 集成

SCM 辅助分析是可选的、由 skill 驱动的。服务可以与 Git、Perforce 等现代 SCM 系统集成，同时保持源码访问只读且由证据把门：只有当构建日志指向源码问题时，Agent 才读取源码上下文。

## 面向各种规模 Studio 的可复用模式

这项服务可以泛化成一个可复用的 Agent 循环模板，适用于各种规模的游戏工作室——从拥有复杂构建农场的 AAA 团队，到 CI 流水线精简的小型初创：

| 模式 | 可复用设计 |
| --- | --- |
| 触发 | 外部系统发出事件，例如 CI 失败、崩溃激增、资产导入失败或构建农场告警 |
| 规范化 | 把异构的平台 payload 转成统一的任务模型 |
| 范围约束 | 证据收集限定在失败构建内，只有日志证明有必要时才扩展到源码上下文 |
| 证据收集 | 先取最直接的证据，只在证据要求时才读更重的上下文 |
| Agent 分析 | 用固定的 prompt 与策略边界，产出可执行的结论 |
| 通知 | 通过可插拔出口，把精简报告送进 Studio 内部工作流 |
| 反馈闭环 | 后续可加入用户反馈、置信度评分、相似案例检索与知识库沉淀 |

## 常见问题

### 服务会为每一次失败都拉取源码吗？

不会。默认流程是日志优先分析。只有当日志证据指向源码问题时，才读取 Git / Perforce 上下文。

### Agent 能自动修代码吗？

不在本服务当前范围内。本服务做的是自动化分析与报告。策略与 prompt 应保持 CI 与 SCM 访问为只读。

### 它支持哪些通知渠道？

服务采用可插拔的通知出口模型。目前支持企业微信，同一接口也可以扩展到 Slack 或其他内部团队工作流。

### 它如何与版本控制系统配合？

SCM 支持由 skill 驱动。Agent 可以与 Git、Perforce 等系统协作，但源码访问保持只读，且只在构建日志证据表明源码相关时才使用。

### 哪些团队适合先接？

先从那些失败频繁、分诊路径重复、日志证据充分，且团队愿意对报告质量给反馈的流水线开始。第一阶段保持只分析日志，在明确能提升根因质量的地方再开启 SCM 辅助分析。
