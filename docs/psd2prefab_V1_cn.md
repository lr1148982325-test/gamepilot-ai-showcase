# PSD2Prefab：打通 Photoshop 与 Unity 之间的游戏 UI 实现断层

当游戏 UI 进入实现与集成阶段，两份主要产物通常都已就绪：美术已在 Photoshop 中完成 PSD/PSB，而开发者已准备好一个包含组件、布局约束与交互的基础 Unity Prefab。剩下的工作是一个高强度的生产环节——把视觉设计准确地翻译进那个已有的功能结构里。

## 1. 真实场景：视觉设计与功能结构都已就绪，但跨工具实现仍然断层

在生产中，游戏 UI 美术与功能开发通常并行推进：

- 美术用 PSD/PSB 的组、图层、文字、形状、效果、剪裁关系与合成顺序，定义界面长什么样。
- 开发者用 `RectTransform`、`Image`、Text/TMP、`Selectable`、`LayoutGroup`、遮罩、动画与事件绑定，定义界面在运行时怎么工作。
- 在 UI 实现阶段，这两份产物必须收敛：每个视觉元素都要映射到正确的功能节点，图层要变成符合 Unity 规范的资产，组件属性要被正确填充，并且结果要与源设计对照复核。

这不是简单导入一个 PSD 就能解决的。设计文件围绕视觉构图组织，而 Prefab 围绕运行时职责组织；命名、粒度与层级很少能对齐。例如，一个按钮在 Photoshop 里可能由独立的背景、描边、图标与标签图层构成，但在 Unity 中对应的是 `Button`、`Image`、TMP 与状态控制节点。实现者必须先理解两边结构，才能决定如何合成、导出、导入与填充。

| 典型场景 | 需要做的工作 | 常见风险 |
| --- | --- | --- |
| 新界面的首次实现 | 理解完整的 PSD/PSB 与 Prefab 层级，再建立视觉元素与功能节点之间的整体映射 | 界面一大，节点发现、资产切图、导入与组件配置就会快速膨胀 |
| 局部设计改版 | 定位受影响区域，重新生成相关资产，并更新对应的 Prefab 节点 | 一次局部改动可能迫使整页重新解读，而写入范围与副作用难以控制 |
| 复杂界面的分区交付 | 独立实现背景、顶栏、内容区、按钮组或状态分支 | 多次走查会引入不一致的命名、裁边、九宫格与 Importer 约定 |
| 视觉与功能联合评审 | 反复比对 PSD/PSB 输出与 Unity UI 的位置、绘制顺序、可见性与视觉保真度 | 上下文碎片化在多个工具、窗口与目录之间，诊断与追溯都很困难 |

每一次设计改版都会重新激活同一串动作：重新找图层、重新生成资产、重新配置组件、再重复一遍跨工具的视觉比对。因此问题不只是「切图慢」；游戏 UI 实现缺少一条连续的工程流水线——能复用上下文、约束写入范围，并强制统一的资产规则。

## 2. 核心问题：视觉结构与功能结构之间没有工程化的映射

Photoshop 和 Unity 各自都不缺核心能力。断层在它们之间：缺少一条为「把游戏 UI 美术实现进已有运行时结构」而设计的连续生产路径。操作员实际上成了一层人工适配器——解读两套层级、在 Photoshop 里识别视觉元素、在 Unity 里定位功能节点、处理资产、配置组件，并通过反复切换工具来验证结果。

这一步把视觉语义翻译成功能语义。它是 UI 交付中操作最密集、最依赖经验的环节之一，并且会被设计变更反复触发。在复杂界面上，视觉图层与功能节点很少一一对应；即便很小的改版也可能需要重新发现、重新导出、重新配置，再来一轮评审。

![PSD2Prefab 结构错配与人工成本飞轮](assets/images/psd2prefab/psd2prefab-problem-model.svg)

| 核心痛点 | 在传统工作流中的表现 | 需要的工程能力 |
| --- | --- | --- |
| 跨工具流程割裂 | 视觉评审与资产准备在 Photoshop，而功能节点、资产配置与运行时校验在 Unity。上下文靠人工搬运 | 把设计源、功能结构、执行进度与评审结果组织在同一个操作工作台里 |
| 跨结构映射困难 | PSD 按视觉构图组织；Prefab 按组件职责组织。命名、粒度与层级通常不同 | 基于结构、类型、位置与视觉证据建立可校验的语义映射 |
| 实现操作密集 | 节点发现、资产确认、导出、裁边、导入、组件配置与视觉评审需要大量连续的手工动作 | 把资产处理、导入、组件填充与预览刷新串成一条可重复的生产流水线 |
| 交付物不一致 | 命名、裁边、复用、九宫格设置与 Importer 属性都取决于个人习惯 | 用确定性规则把资产与组件属性标准化 |
| 迭代复用率低 | 一次局部视觉改动可能触发整屏重新解读与处理 | 通过显式上下文与受限的写入范围，支持定向重跑 |
| 评审证据碎片化 | 设计图层、功能节点、资产设置与运行时结果分散在多个工具和目录里 | 把设计预览、运行时输出、映射关系、日志与恢复状态放在一起呈现 |

## 3. 产品定位：面向已有 Prefab 的 UI 实现工作台

> **把 Photoshop 到 Unity 的 UI 实现环节，收进一个统一的 Unity 工作台。**

PSD2Prefab 是一个嵌在 Unity Editor 里的游戏 UI 实现工作台。它把 PSD/PSB 的视觉信息、已有 Prefab 的功能结构与 Unity 资产规范，收进同一个任务上下文。语义映射负责提出设计元素与功能节点之间的对应关系；随后一条确定性流水线执行校验、视觉烘焙、资产规范化与导入、Prefab 填充、预览刷新，以及从失败的 Apply 中恢复。

当需要 Photoshop 来做更高保真的视觉处理时，插件也会编排对它的调用与产出收集，减少两个应用之间上下文与中间产物的人工搬运。首次整屏实现可以用全局自动匹配。大界面、局部改版与增量修复，可以在选定的 Scope 内用局部自动匹配。两种尺度共用同一套资产处理与交付规则。

| 项目 | 产品契约 |
| --- | --- |
| 输入 | 一个 PSD/PSB 文件与一个已有的 Unity UGUI/TMP Prefab |
| 输出 | 已填充的目标 Prefab，外加写入 `_Res` 或已配置 `Assets/...` 目录的精灵图、栅格化文字兜底与所需的 TMP TextFX 材质 |
| 统一工作台 | PSD/PSB 解析、视觉证据、Prefab 结构、映射关系、生产进度与评审结果在同一个 Unity 工作台内协同完成 |
| AI 职责 | 基于结构、类型、空间与视觉证据，提出 PSD 节点与 Prefab 节点之间的语义映射 |
| 工程流水线职责 | 校验映射，并执行烘焙、裁边、去重、九宫格检测、导入、填充、预览刷新与 Apply 失败恢复 |
| 结构原则 | 保留已有 Prefab 作为功能基线。工具不会随意删除、重排或重建整个应用界面。它只在显式策略下创建工具自有的 `_AI` `Image`/`RawImage` 节点，或执行受控的文字组件适配 |
| 匹配范围 | 既支持跨完整源 / 目标层级的全局自动匹配，也支持当前 Scope 内的局部自动匹配 |

产品边界是 UI 实现这一环节。PSD2Prefab 不替代视觉设计、功能性 Prefab 搭建、交互逻辑、动画制作或最终人工评审。自动匹配只产出映射提案；确定性校验与用户确认共同约束实际的写入范围。

这一定位不同于通用的 design-to-code 系统。PSD2Prefab 并不试图重新生成一个「看起来差不多」的界面。它把视觉实现整合进已有的项目结构，保留既有功能结构，并产出仍然适合继续开发、集中评审、以及 Apply 失败时可恢复的 Unity UI 资产。

## 4. 统一工作台体验

Unity Editor 插件提供一个可调整宽度的四栏工作台，把结构查看、Scope 选择、任务执行与结果评审收进同一个窗口。

![带功能区域标注的 PSD2Prefab Unity 工作台](assets/images/psd2prefab/psd2prefab-workbench-annotated.png)

*工作台在同一个 Unity 窗口里呈现 PSD/PSB 与 Prefab 结构、选中节点预览、双实时预览、Properties、Scope 控件与匹配操作。完整根层级支持全局自动匹配，而选中的 PSD Group 与 Prefab Container 则定义一个聚焦的局部自动匹配 Scope。*

| 区域 | 主要信息与操作 |
| --- | --- |
| PSD 结构 | PSD/PSB 的组、图层、文字、形状、可见性、边界与层级 |
| Prefab 结构 | Prefab 层级，外加 `RectTransform`、`Graphic`、`Image`、Text/TMP、`Selectable` 与布局信息 |
| 实时预览 | 上方渲染 Prefab、下方渲染 PSD/PSB，支持缩放、平移、适配、100%、聚焦框选与拾取 |
| 详情 | Properties、可选的 Control Library、Settings、Log，以及所选节点的来源、质量状态、资产、诊断与可编辑属性 |

这些树、预览拾取、节点检视弹窗与 Properties 面板共用同一套节点身份与选中模型。用户可以在树里选中节点、双击聚焦，或直接在预览里拾取。在同一位置反复点击，会按实际的从前到后顺序在重叠节点之间循环。

预览可见性与业务 Scope 相互独立。Eye、Show All、Restore Source、缩放、平移、适配、聚焦与拾取只影响观察状态；它们既不改变自动匹配的输入，也不改动源 PSD/PSB 或 Prefab。

属性修改使用一条独立、需显式发起的编辑路径。Prefab 属性通过受控的 Unity 侧服务应用；写回源 PSD 属性则需要 Photoshop。这条路径不改变普通预览操作的只读契约，也不会给 AI 授予写权限。

## 5. 核心工作流

![PSD2Prefab 核心工作流](assets/images/psd2prefab/psd2prefab-core-workflow.svg)

### 5.1 全局与局部自动匹配

自动匹配通过同一套底层能力支持两种处理尺度。Scope 并不是「局部模式」的同义词；它同时定义了一个任务的匹配上下文，以及后续 Apply 操作可以修改的范围。

| 模式 | Scope 选择 | 推荐使用 |
| --- | --- | --- |
| 全局自动匹配 | 把完整的 PSD/PSB 根层级与完整的 Prefab 根层级纳入 Scope | 首次整屏实现、中等体量界面，或建立完整的视觉到功能映射 |
| 局部自动匹配 | 选中对应的 PSD Group 与 Prefab Container | 大界面、局部改版、状态分支、增量修复，或失败后更小范围的重跑 |

两种模式共用同一套 Context、Visual Evidence、LLM Mapping、Normalize/Validate、Bake、Import、Fill、Preview Refresh 与 Rollback 契约。对特别复杂的界面，先查看完整结构，再从中等大小的 Scope 开始——例如背景、顶栏、主内容区或按钮组。验证通过后再扩大 Scope。

LLM 会综合两侧层级、节点路径、节点类型、位置、尺寸、当前 Scope、视觉证据、项目级 Mapping Instructions，以及可选的 Control Library 信息。它只返回一个结构化的映射提案。插件随后对该提案做归一化与确定性校验。如果部分建议因为目标缺失、重复冲突或类型不兼容而被拒，用户必须先确认有效的那部分子集，才会发生任何写入。

### 5.2 手动填充

当视觉源与功能目标之间的关系已经明确时，手动填充可以绕过 LLM：

- 一个或多个 PSD 图像图层或 Group → 一个 Prefab `Image`、`RawImage` 或 `Selectable` Graphic。
- 一个 PSD 文字图层 → 一个 Prefab Text/TMP 组件。
- 多个 PSD 源 → 一张合成后的目标精灵图。

如果所需字体资产不可用且允许视觉兜底，插件可以在用户确认后创建或复用一个受控的 `_AI` `Image` 节点来显示栅格化文字。它不会随意生成新的应用控件结构。手动填充复用与自动匹配相同的 Validate、Bake、Trim、Deduplicate、Nine-slice、Import、Fill 与 Preview Refresh 规则，确保自动化与手动两条路径的资产标准一致。

### 5.3 确定性资产生产

映射通过校验后，插件先在 Session 工作区完成视觉烘焙。在生成最终资产或修改目标 Prefab 之前，它会创建一个还原点，然后执行一条确定性的 Apply 计划：

1. 烘焙映射选中的 PSD 图层或 Group。
2. 快照目标 Prefab、`.meta` 文件、资产目录与相关的 Importer 状态。
3. 裁掉透明边界，按内容复用重复图像，并检测可复用的边框。
4. 把精灵图写入并导入到 Prefab 相邻的 `_Res` 目录，或用户配置的 `Assets/...` 路径。
5. 把图像、文字、可见性与布局结果应用到已有的 Prefab 节点上。
6. 刷新 Prefab 预览，以便与 PSD 预览并排评审。

九宫格参数不由 LLM 决定。只有当检测到有效、非零的边框，且目标是一个兼容切片的 `UnityEngine.UI.Image` 时，插件才会写入 `TextureImporter.spriteBorder` 并把 Image 类型设为 `Sliced`。`RawImage` 与 Filled Image 组件保持其既有语义。

## 6. 系统架构与职责边界

PSD2Prefab 把表现层、编排层、语义分析层与确定性生产层分开。这些层通过受约束的数据契约协作，而运行时中间产物、最终资产与目标 Prefab 各自处在不同归属边界内。

![PSD2Prefab 系统架构](assets/images/psd2prefab/psd2prefab-architecture.svg)

关键的架构边界是：

- **观察边界：** 树、预览、Properties 与 Scope 属于表现层。普通的预览交互永不写入资产。
- **AI 权限边界：** 语义层只产出映射提案；它没有写 Prefab、精灵图或 Importer 设置的权限。
- **来源边界：** PSD 侧数据来自 Photoshop 视觉输出或 Runtime Reader；Prefab 侧数据来自 Unity 内部的结构与组件检视。
- **自动化生产写入边界：** 自动匹配与手动填充只有在校验通过后，才通过确定性生产服务调用 Bake、资产导入、Prefab 填充与回滚。
- **显式属性编辑边界：** 属性修改由用户提交，由确定性属性服务执行。源 PSD 写回仅在 Photoshop 路径下可用。
- **存储边界：** 运行时中间产物位于 `Library/Psd2Prefab/Sessions/<sessionId>/`；最终视觉资产位于 `Assets/...`；目标 Prefab 接受受控修改，同时保留其既有功能结构作为基线。

## 7. 运行时协作

对一个自动匹配任务，工作台负责组织输入与 Scope，语义层产出映射提案。工作台与确定性服务随后对提案做归一化、检测冲突，并在需要时请求用户确认。校验通过后，生产流水线在 Session 工作区完成烘焙，在写入最终资产或改动目标 Prefab 之前创建还原点，然后执行资产导入、Prefab 填充与预览刷新。运行时协作如下所示。

## 8. 安全、质量与运行时边界

### 8.1 预览与源资产隔离

- Prefab 预览使用 Unity 预览场景中的只读克隆。它不会打开独立的 Prefab Mode，也不会修改源 Prefab。
- 初始 PSD/PSB 视觉源建立之后，Eye、拾取、缩放、平移、适配、聚焦与选中只更新内存状态与渲染输出。
- 预览选中、预览可见性、源可见性与业务 Scope 是四种相互独立的状态；Eye 状态永远不会污染 Mapping、Bake 或 Fill 的输入。
- 普通预览交互永远不会重新启动 Photoshop、重新解析 PSD、重新上传纹理或写入磁盘。

### 8.2 Photoshop 与 Runtime Reader

| 模式 | 最适合 | 质量边界 |
| --- | --- | --- |
| Photoshop | 高保真的生产烘焙，以及复杂文字效果、智能对象、高级混合等内容的处理 | 首次冷处理可能较慢。对于涉及复杂效果的任意图层可见性组合，不保证逐像素一致。处理完成后，普通预览交互不会再调用 Photoshop |
| Runtime Reader | 没有 Photoshop 的环境、快速浏览结构、标准图层与简单文字。它也可以作为降级的生产烘焙路径 | 复杂混合、调整图层、智能对象与 Photoshop 专属效果会被近似处理 |

### 8.3 校验与恢复

| 阶段 | 保护 |
| --- | --- |
| 映射 | 在写入前检查目标缺失、重复冲突、类型兼容性与结果完整性 |
| Apply 之前 | 快照 Prefab、`.meta` 文件、完整的目标资产目录与相关 Importer 状态 |
| Apply 期间 | 最终资产写入与 Prefab 填充遵循确定性计划；绝不接受 LLM 自由格式的属性写入 |
| Apply 失败 | 还原点建立之后，任何资产写入或 Prefab Apply 失败都会触发自动恢复。也可以显式调用 Rollback Restore |
| 运行时产物 | Context、Evidence、Cache、Log 与还原点数据位于 `Library/Psd2Prefab/Sessions/<sessionId>/` |
| 最终资产 | 精灵图、栅格化文字兜底与 TMP TextFX 材质位于 Prefab 相邻的 `_Res` 目录或用户配置的 `Assets/...` 路径 |

### 8.4 模型请求与配置边界

- 自动匹配会把当前 Scope 内的 PSD/Prefab 结构上下文、视觉证据、Mapping Instructions 与可选的 Control Library 信息，发送到一个用户配置的 Azure/OpenAI 兼容端点。手动填充不发出 LLM 请求。
- 发送请求之前，插件会在本地校验图像数量、单张与聚合像素数、prompt 字节大小与请求体总大小。超限的请求会被拦下，并把实测数值报给用户。
- API key 存放在当前 Windows 用户的 Unity `EditorPrefs` 中。它不会写入项目的 `settings.json`、不会随 `Assets` 提交，也不会包含在交付包里。

## 9. 能力范围与运行要求

### 9.1 当前能力

| 能力 | 当前行为 |
| --- | --- |
| 结构与属性检视 | 在同一个 Unity 窗口里查看 PSD/PSB 与 Prefab 的层级、类型、边界、组件与属性 |
| 双实时预览 | 通过 Unity 预览场景渲染 Prefab，通过 Photoshop 或 Runtime 分层视觉源渲染 PSD |
| 统一的选中与检视 | 树、预览拾取、聚焦、节点检视弹窗与 Properties 共用同一套节点身份 |
| 显式属性编辑 | 在 Properties 中查看并提交受支持的 PSD/Prefab 属性修改。写回源 PSD 属性需要 Photoshop |
| 全局 / 局部 Scope | 覆盖完整的源与目标层级，或把推理与 Apply 约束在某个面板、按钮组或状态区域内 |
| AI 自动匹配 | 从结构与视觉证据生成映射提案，再经确定性校验后才写入 |
| 手动填充 | 对已知的一对一或多对一关系绕过 LLM，同时复用确定性生产流水线 |
| 资产生产 | 烘焙、透明边裁切、基于内容的去重、九宫格检测、Unity Sprite 导入，以及所需的栅格化文字与 TMP TextFX 材质生产 |
| Prefab 填充 | 填充图像、文字、可见性与布局，同时保留既有功能结构。在显式策略下，创建工具自有的 `_AI` `Image`/`RawImage` 节点或执行文字组件适配 |
| 可选 Control Library | 浏览可复用的项目控件与属性模板，并为当前目标节点暂存模板属性 |
| 失败恢复 | 在 Apply 之前创建还原点，写入失败时自动回滚，并支持显式回滚 |

### 9.2 环境与依赖

| 项目 | 要求 |
| --- | --- |
| 运行环境 | Windows 与 Unity Editor。当前已验证的基线是 Unity `2021.3.36f1c1` |
| Python | 推荐 Python `3.10+`。后端依赖必须装进插件里配置的同一个解释器 |
| UI 框架 | 支持 UGUI。目标 Prefab 使用 TMP 的项目必须安装并初始化 TextMeshPro |
| 自动匹配 | Azure/OpenAI 兼容的 Chat Completions 端点 |
| 手动填充 | 不需要 LLM 端点 |
| Photoshop | 可选。建议用于更高保真地解析与烘焙复杂 PSD 内容 |
| 输出目录 | Prefab 相邻的 `_Res` 目录，或另一个有效的项目内 `Assets/...` 路径 |

### 9.3 当前限制

- 一个任务处理一个 PSD/PSB 与一个目标 Prefab。
- PSD2Prefab 不会从零自由生成完整的 Unity 界面架构。
- 单个任务不会把多个 PSD 文件合并进一个 Prefab。
- 自动匹配是一项受校验与用户确认约束的辅助实现能力；它不替代最终的视觉评审。
- Properties 只暴露受支持的属性编辑，并不是 Unity 内部 Photoshop 的完整替代品。
- Runtime 模式不保证复杂 Photoshop 效果的逐像素一致渲染。
- 大界面需要依据节点数量、视觉复杂度与模型预算来选择合适的 Scope。
- `LayoutGroup`、嵌套 Prefab 与项目专属组件仍受 Unity 与项目自身约束。
