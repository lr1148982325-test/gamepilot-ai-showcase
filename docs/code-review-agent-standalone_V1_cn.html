Code Review Agent

面向游戏工作室的多视角 AI 代码评审

多数 AI 代码评审只会给出一份针对 diff 的「通才式」意见。这类意见的浅薄是可预见的：能发现缺失的判空，却漏掉网络复制（replication）失同步，最后建议改个变量名。单一评审者配单一 prompt，就只有一把尺子，所有问题都被压平到这把尺子上。

Code Review Agent 会从四个独立视角同时评审每个改动——逻辑、安全、质量、性能。每个视角都是一个独立的子 Agent，有各自的关注点、各自的置信门槛，以及一份明确的「拒绝报告清单」。它们并行运行，结论汇总时：一个既是崩溃又是漏洞的缺陷只上报一次并取更高严重级；纯风格细节则无人上报。

1. 定位与架构

服务层负责编排，评审逻辑位于 GamePilot CLI。Agent 检测到变更、判断是否在处理范围内、调用 CLI 的 /review skill，再把结果回帖到团队日常协作的地方。

组件 职责
Perforce / Git 唯一数据源，只读
Swarm + AI CR 插件 在 changelist 上触发评审事件；GitLab 与工蜂 Webhook 承担同样角色
Code Review Agent 队列、范围过滤、调用 CLI、回帖评论、通知。不做评审判断
GamePilot CLI（/review） 解析目标并运行四个评审子 Agent。分析在这里发生
AI 后端服务 知识检索与按工作室配置
Elasticsearch 工作室规则索引，按 diff 查询
Langfuse + Postgres 链路追踪、评测与运行状态
LLM 唯一位于工作室网络边界之外的组件，可自建或云端托管

除推理外，所有组件都运行在工作室内网。

关于代码库的说明。 评审服务里还留着一套较早的进程内评审引擎，那条路径已属遗留。当前版本委托给 GamePilot CLI，意味着评审行为随工程师本地运行的同一套工具链一起版本化——因此在合并请求上评论的评审者，就是工程师提交前能在本地跑起来的那套评审者。

2. 四个视角，同一份 diff

每条 track 问的是不同的问题。这种划分不是摆设——每个子 Agent 有各自的方法，并会把属于同级的问题明确移交出去。

Track 问题 方法 拒绝报告
逻辑 正确吗？ 意图优先、契约优先。识别谁负责该行为、什么定义了正确性，并沿改动追踪数据路径 风格、缺失测试、主观设计、任何 linter 能抓到的问题
安全 可被利用吗？ 从源到汇（source-to-sink）。跨越信任边界追踪攻击者可控输入直至特权 sink，定位缺失的防护 泛泛的加固建议、「最佳实践」、任何无法构造出利用路径的问题
质量 会崩溃吗？ 对改动范围执行 12 类引擎原生检测 格式、命名、纯性能问题、纯安全问题
性能 关键路径上够快吗？ 位置与规模。指出改动给可达热路径新增的无效开销，并点名更省的做法 微优化、任何需要 profiler 才能确认的问题、任何以牺牲正确性换速度的问题

每条 track 实际在找什么

逻辑 —— 分支与边界错误、循环终止、状态与序列化缺陷、事件顺序与异步生命周期问题、破坏既有调用方的契约不匹配，以及只堵住表象却留下另一条可达路径的修补式改动。针对游戏代码，它特别关注 Tick 循环、冷却、技能规则、存档/读档状态、客户端/服务器权威、预测与多人失同步。

安全 —— 注入、路径穿越、不安全的反序列化、鉴权与归属绕过、密钥泄露、不安全的加密。落到游戏语境：服务器权威被破坏、RPC 滥用、经济系统与存档篡改、反作弊绕过。判定门槛刻意设得很严——出现 UFUNCTION(Server, ...) 或 [ServerRpc] 本身并不构成问题；只有当它能点名攻击者可控的源、跨越的边界、缺失的防护与特权效果时，才会上报。

质量 —— 这是最贴近引擎的评审者，覆盖 Unreal C++、Unity C#，以及 Lua / TypeScript 编写的 UE 玩法脚本。12 个类别是：生命周期与悬垂引用；释放后使用与移动后使用；空指针与无效对象解引用；未初始化状态；数值正确性；除零；恒真/恒假条件；资源泄漏；并发与竞态；容器与引擎 API 误用；死代码；以及会诱发崩溃的可维护性风险。它寻找的证据是真正引擎相关的——对 GC 不可见的裸 UObject* 成员、未校验的 TWeakObjectPtr、pending kill 之后的访问、容器重分配后仍被使用的元素引用、比其 UObject 活得更久的脚本侧代理、跨场景重载仍存活的 Unity 引用。

性能 —— 每帧、Tick、渲染、物理、AI 或网络复制路径上新增的开销；热循环里的分配、字符串格式化与反射；意外的平方级扫描与全场景搜索；玩法路径上的同步资源或着色器加载；无上限缓存与泄漏的订阅；每帧可靠 RPC，以及随玩家数快速劣化的 per-client 工作。

为什么这种划分立得住

有三个特性让它不只是「四个 prompt 披一件风衣」：

刻意移交。 质量评审者不会上报纯性能或纯可利用性问题——它把这些交给同级。这正是防止每条 track 退化成通才的关键。什么都能报的评审者，最后什么都会报。

按 track 自证。 在输出任何结论前，每个评审者会先给自己的候选问题打上 CONFIRMED、PLAUSIBLE 或 REFUTED。确证要求点名触发条件——抵达该缺陷的输入、状态或时序——并引用造成它的改动行。否证要求引用使其成为非问题的防护代码。默认 effort 下只输出确证结论；安全 track 在任何级别都偏向精确率。

一致提升的是置信度，而非数量。 汇总时按文件、行范围、根因与修复建议对重叠结论去重。两条 track 一致时，该结论保留两个标签并取更高严重级。输出按 effort 档位设上限，严重级高的优先。

3. 控制范围与深度

评审可在两个维度上调节，这很关键——提交前检查与发布分支审计不是同一件事。

维度 选项 效果
Track 选择 --scope all / logic / security / quality / performance 运行哪些评审者。工作室可以只启用自己信任的部分
深度 --effort low / medium / high low 是只扫改动块的快速模式，不做自证。medium 偏向精确率。high 扩大搜索范围、增加补漏扫描并转为偏向召回率——会输出带不确定性说明的合理结论

结论字段包含 file_path、track、line_range、severity、issue、why、failure_scenario 与 suggestion。其中 failure_scenario 在实践中最有用：它迫使给出具体触发路径，而不是一句含糊的警告。

4. 把工作室规范变成版本化产物

通用评审者会漏掉工作室特有的东西。团队把约定提交进仓库，评审者会遵守它们。

  • REVIEW.md（位于 .gamepilot/、.gpc/ 或 .rdec/ 下）用于校准严重级、设置细节类问题的上限、添加仓库专属检查，并可选择运行哪些评审 track。工作室可以默认关闭性能 track，或把质量类结论限制在高严重级及以上。
  • 规则文件与 AGENTS.md 在 push 时同步进规则索引，并按 diff 检索。删除文件即撤回规则，因此规范不会在无声中与代码库脱节。
  • 检索到的规则被视为高于模型通用先验的权威，其中工作室私有规则优先于公共默认规则。

这正是把通用评审者变成「本工作室的」评审者的机制；实践中，它对精确率的提升超过任何一次模型选型的调整。

5. 覆盖范围与边界

领域 覆盖范围
语言 C/C++、C#、Lua、Python、TypeScript/JavaScript、Java、Go 及其他常见源码类型
引擎 Unreal（C++、Blueprint 检查、玩法脚本）与 Unity（C#）
版本管理 Perforce、Git、GitLab、工蜂
默认排除 删除的文件、二进制文件、生成产物、测试与 mock、lockfile、配置、压缩打包产物、文档。Blueprint 资产仅在被显式指定时才评审

诚实的局限：

  • 结论必须锚定到改动行。这是正确的取舍，但也意味着 Agent 不会去报一个改动「恰好挨着」的既有缺陷。
  • 它评审的是有边界的改动，不是整个系统。它不会告诉你架构错了。
  • 严重级会被上报并用于排序，但它不是合并门禁——门禁策略归团队所有。
  • 评审质量依赖可检索的上下文。使用 Perforce 的工作室必须把源码同步进服务；否则评审者会失去确证门槛所依赖的跨文件证据。
  • 来自 Jira / TAPD 的单据文本被视为不可信输入，因为在某些工作流中它可能受攻击者影响。
  • 人工评审仍是最终验收方。

6. 常见问题

为什么是四个评审者，而不是一个好 prompt？ 因为单一评审者只有一把尺子。拆分之后，每条 track 可以按自身领域设定合适的门槛——安全要求可构造的利用路径，性能要求已证实的热路径——并各自拒绝那些让 AI 评审变吵的类别。

这会让评审成本翻三倍吗？ 各 track 并行运行，且 track 可选。工作室可以只跑逻辑与质量，或用 --effort low 做快速提交前检查，把完整集合留给发布分支。

它能改代码吗？ 不能。所有源码访问都是只读。修复建议写在 suggestion 字段里。

各部分跑在哪里？ 服务负责编排，CLI 负责评审。同一套评审者定义既跑在工程师的终端里，也跑在服务端评审中，因此提交前与推送后的反馈是一致的。

工作室该从哪里起步？ 一个仓库、评论式建议、两条 track。然后把资深同学在评审里反复强调的约定写下来——这一步对精确率的提升胜过其他任何事。
