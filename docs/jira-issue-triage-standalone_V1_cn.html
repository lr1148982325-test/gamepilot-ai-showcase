基于 DevPilot 的 Jira 问题分诊

面向重复研发流程的声明式 Agent

每个工作室都有一支没人愿意接的队列：需要做首轮处理的 incoming 缺陷报告。总得有人把每一条读一遍，判断它是不是上周提过的重复单，收集显而易见的证据，猜一个可能的负责人，然后写下来。相对于做这件事的人来说它没什么技术含量，又永远不够紧急到能排进日程，却悄悄决定了真正的缺陷能被多快修掉。

DevPilot 把这道首轮处理自动化了。它是一个通用 Agent 运行时——一个把 Webhook 与 cron 触发转成持久化、沙箱化 Agent 运行的单进程——而 Jira 分诊是它最成熟的应用。值得关注的设计押注是：一个 Agent 是一个装着 YAML、Markdown 与 JSON Schema 的文件夹，而不是代码。新增一项自动化意味着写一份 playbook 和一个输出契约，而不是发布一个 TypeScript 模块。

1. 精力真正花在哪

分诊任务 人今天怎么做 Agent 怎么做
重复单识别 隐约记得有张类似的单，搜一下，在时间压力下放弃 有条理地检索，并给出带推理的候选重复单
证据收集 打开单子，读评论，可能下载一份日志 拉取原始 issue 与评论，必要时检查附件
初次看代码 通常跳过 可选地读取一份只读代码检出作为辅助上下文
负责人猜测 在群里问，或者就空着 基于证据给出负责人提示
写下来 不统一，常常干脆不写 每个 issue 一条结构化的结论评论

目标不是关闭问题。目标是确保当人打开一张单子时，那些枯燥的工作已经做完并且可见。

2. 运行时架构

有三个属性比框图更重要：

接入层只记录，不干活。 Webhook 或 cron 触发被规范化成一次运行请求，写进 SQLite 队列后立即返回。去重键成为运行 id，唯一性由数据库保证——因此一条重投的 Webhook 是一次空操作，而不是第二次运行。被中断的运行通过租约到期被回收，而不是丢失。这里刻意做成单实例：队列是一份本地持久化日志，不是分布式消息中间件。

沙箱是声明出来的，不是默认的。 一个步骤默认没有任何工具。每个 pack 要显式选择一种工具 profile——只读、工作区，或带 bash 的沙箱——而最强的那档 profile 在没有操作系统级沙箱后端时拒绝启动，而不是悄悄降级。这一点很关键，因为分诊 Agent 会读可能被攻击者影响的文本：一份缺陷报告里可能夹带指令。隔离在每次文件系统调用时按解析后的真实路径强制生效，因此符号链接无法逃出工作区；网络出口默认拒绝，除非 pack 明确列出允许访问的主机。

密钥是挂载进来的，不会被追问。 凭据以挂载文件和环境变量的形式进入沙箱。模型只被告知变量的名字，永远拿不到值，playbook 也被指示绝不要打印它们。

3. 分诊流程

这个模式是一个调度器 + 一个工作器——两个 pack，一种关系。

调度器按工作日早晨的 cron 运行，查询一个已保存的 Jira 过滤器，并为每个 issue 产出一条工作项。使用已保存过滤器是关键的设计选择：团队在 Jira 里管理分诊范围，就在他们本来就管查询的地方，而不是在 Agent 配置里。

每条产出的工作项变成一个独立入队的工作器运行。这正是它稳健的原因——五十个 issue 就是五十次运行，各自独立重试、各自留痕、可审计。一张格式错误的单子不会拖垮整批，分诊质量也不会像五十张单子共用一个 prompt 那样劣化。

在单次工作器运行内部：拉取原始 issue 作为主要证据、查重、可选地查阅一份只读代码检出，然后按严格 schema 产出结论——状态、风险、发现、建议动作、负责人提示、证据与局限。

工程真正吃劲的地方在三个细节：

  • 去重键包含最后更新时间戳，因此一条真正被更新过的 issue 会产生一次新运行，而不是被永久去重掉。
  • 空结果必须诚实。 如果 Jira 返回鉴权或网络错误，发现阶段就大声失败。一个坏掉的凭据绝不能把自己伪装成「今天没有待分诊的 issue」。
  • 标签是收尾闸门。 处理标签只在结论评论成功之后才打上，然后回读校验。任一步失败，运行以 needs-human 结束。评论与标签不会出现漂移，这正是每日循环可以安全重复执行的原因。

4. 范围纪律

除恰好两个写操作——一条结论评论和一个处理标签——之外，Jira 访问是只读的。Agent 不能流转状态、改派、改优先级、关闭或编辑其他字段。

这是一条刻意的信任边界。分诊要赢得采用，靠的是可逆——一条错误的评论忽略掉成本很低，而一次错误的状态流转会打乱别人的迭代。同样思路的辅助约束：附件按大小与类型设闸，文件名按不可信处理；评论从文件发出，因此 Markdown 不会被 shell 引号搞坏；挂载的代码检出是一次性副本，改动会被丢弃。

5. 为什么用声明式 pack

一个 pack 就是一个目录：agent.yaml 放触发器、配置与流水线；Markdown playbook 放指令；JSON Schema 放输出契约；外加可选的可复用 skill。pack 在启动期校验——重复 id、缺失 playbook、非法 schema、skill 不匹配都会快速失败，而不是等到周一早上九点。

步骤类型 用途
agent 让模型执行一份 playbook，并按 schema 校验输出。
dispatch 同上，但把每条产出的工作项扇出为子运行。
checkout 浅克隆 git 仓库以获取代码上下文。
publish 渲染声明好的 sink 并写入一份回执。
hitl 人工介入（human-in-the-loop）占位。
refresh 重新探测可能已过期的事实。

回报是 Jira 分诊这套做法可以推广。同一套运行时已经承载了 Jenkins 构建失败分析器，而调度器/工作器这套形状适用于任何「扫一个队列、扇出、逐项处理」的问题——flaky 测试、崩溃聚类、依赖告警、长期无人处理的评审请求。

6. 诚实的实现状态

这是一个在积极开发中的可用系统，不是完成品。直说：

能力 状态
触发 → 持久化队列 → 沙箱化 Agent → schema 校验 JSON 真实，端到端可用
调度器扇出子运行 真实
Jira 读取、结论评论、分诊标签 真实 —— 由 Agent 在沙箱内通过 Jira CLI 执行
cron 调度、去重、重试、租约回收 真实
publish sink 本地桩实现。 会渲染并写一份回执文件，不调用任何外部系统。
hitl 人工审批 本地桩实现。 写一个 pending 文件后返回，不会阻塞等人。
refresh 部分。会跑探测，但不会对矛盾采取行动。
Token 预算 已声明并上报，但只强制执行墙钟时间上限。

两点容易搞错的澄清。第一，真实的 Jira 写操作发生在 Agent 步骤内部、经由 Jira CLI——不是通过 publish sink，后者仍是桩。第二，TAPD 尚未实现。 当前的集成是 Jira 与 Jenkins。TAPD 是自然的下一个目标，因为 pack 模型把改动隔离到一份新 playbook 加一个 CLI 或 API 接口，但今天没有为它交付任何东西。

7. 边界

  • 分诊产出的是建议，不是决定。路由与优先级仍归人。
  • 重复识别是带推理的候选列表，不是权威的合并操作。
  • 代码上下文是辅助证据；issue 自身数据仍是事实的主要来源。
  • 外部 CLI 必须在宿主机上安装并配置好——Agent 不会去装它，而是上报缺失的依赖，而不是瞎猜。
  • 单活实例，依赖持久化本地卷。不是 active-active 队列。
  • 投递是至少一次，因此未来任何外部 sink 都必须是幂等的。

8. 常见问题

为什么用 cron 而不是 Jira Webhook？ 早晨批处理符合分诊结果被消费的实际方式；对已保存过滤器跑一次调度器，比对每个字段变更做反应更便宜、也更容易推理。如果需要逐事件分诊，运行时里也有 Webhook 触发器。

怎么防止它无休止地重复分诊同一个 issue？ 靠处理标签，在发现阶段检查。它同时充当幂等键，这也是标签写入要以评论写入成功为前提的原因。

如果模型返回了格式错误的东西怎么办？ 该步骤校验失败并按策略重试。一次运行永远不会发布未校验的输出。

它能修自己分诊出来的缺陷吗？ 运行时支持委派给编码 Agent，pack 模型让这成为流水线里的一个步骤，而不是一次重写。今天分诊 pack 停在给出结论——在信任建立期，这是正确的停手位置。

TAPD 要怎么接进来？ 为 TAPD 的查询接口写一份新的调度器 playbook，再为其评论与标签操作写一份工作器 playbook，复用同一套队列、沙箱、扇出与 schema 校验机制。运行时不是 Jira 专用的；只有那两份 playbook 是。
