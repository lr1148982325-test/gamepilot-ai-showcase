# GamePilot 研发知识库 + DeepWiki：把项目上下文变成可复用的 AI 能力

游戏研发知识很少集中在一处。架构藏在源码仓库里，环境搭建说明散落在各个 wiki 页面，设计意图分散在文档与表格中，而重要决策留在单据或聊天记录里。这种碎片化对人和对 AI Agent 的影响是一样的：两者都必须先重建项目上下文，才能做有用的工作。

GamePilot 研发知识库 + DeepWiki 把这种分散的上下文，变成一条可维护、带权限感知的知识供给链。DeepWiki 先把游戏代码库转成可导航的技术 wiki；知识库再把这份代码理解与项目文档结合起来，并向上手引导、编码、评审、设计、QA 与运维等流程提供有依据的上下文。

本 Showcase 聚焦于真实工作流中被解决的问题、可复用的架构，以及在工作室项目中已被验证的部分。

## 1. 背景：项目知识是存在的，但无法被稳定复用

一个游戏项目会产出大量有用的知识，但它的形态与归属让复用变得困难。

| 知识所在 | 实际问题 | 流程影响 |
| --- | --- | --- |
| Perforce、Git 与 SVN 仓库 | 架构与实现意图必须从庞大且快速变化的代码库中反推 | 新开发者不知道该先读哪些系统或文件；编码 Agent 缺少项目专属上下文 |
| Confluence、iWiki 与共享文档 | 搭建指南、规格说明、设计规则、表格、图片与公式被工具和组织切分开 | 人们反复在多个系统里搜索，并手工核对相互冲突的版本 |
| Jira、TAPD 与 Slack | 决策与归属信息容易丢在单据历史或对话里 | 某个 API、规则或设计约束背后的原因，常常在最终的实现上下文里缺失 |

把每个数据源直接接到 Agent 上并不能完全解决问题。各自独立的关键词检索返回的是 top-N 片段，缺乏共享的语义模型、一致的排序、来源治理与项目结构。Agent 仍然得自己拼装上下文，不相关的分块会吃掉它的上下文窗口，而过时信息可能被当成当前指导。

因此目标不是一个庞大的文档门户，而是一项可复用的工程能力，用来回答一个更窄的问题：**工作室如何持续地把原生项目数据，转成可供特定研发任务信赖的上下文？**

## 2. 可复用的架构

这项可复用能力由两个协作组件构成：

- **GamePilot DeepWiki** 把源码仓库转成结构化的技术知识与自然语言代码导航。
- **GamePilot 知识库服务** 接入 DeepWiki 的产出与经审批的非代码来源，维护可检索的知识，并向 AI 工作流提供面向任务的上下文。

![DeepWiki 与知识库架构](assets/images/deepwiki/deepwiki-architecture.svg)

这种切分让工作室可以渐进采用。团队可以先只通过 DeepWiki 建立代码理解，再接入少数高价值项目来源，并把得到的知识集成到选定的 Agent 工作流中，之后才扩大覆盖范围。

## 3. Showcase 1 —— 从陌生的 depot 到可用的心智模型

### 实际问题

新开发者加入一个大型游戏项目，必须理解架构、配置工作站、学习提交规则、弄懂项目术语，并找到系统负责人。这些答案可能存在，但分散在源码、搭建页面、团队文档与过往排障记录里。

昂贵的部分不是读某一篇文档，而是找出正确的阅读顺序，并验证每条说明是否仍与项目相符。

### 知识库如何改变工作流

1. 开发者向 DeepWiki 索取相关玩法或引擎系统的高层地图。
2. 答案指出主要子系统之间的关系，并把开发者链到支撑性代码与资产。
3. 知识库从已审批的项目来源中，检索当前的工作站检查清单、常见构建修复与提交规则。
4. 项目术语表解释缩写与内部工具名，而归属知识指出负责该子系统的团队或个人。
5. 追问会收窄路径，例如：「玩法技能的网络复制如何到达服务器权威，我应该先读哪些文件？」

![DeepWiki 同时呈现可导航的架构地图与有仓库依据的问答](assets/images/deepwiki/deepwiki-architecture-query.png)

*DeepWiki 把生成的架构地图、源码导航与有仓库依据的问答合并在一个视图里。*

### 结果

新人上手的交付物变成一条可复现、有证据支撑的路径，而不是一堆书签和个人讲解。同一能力还能支撑不同角色：开发者可以追溯运行时架构，设计师则可以查询某个玩法特性背后的配置与归属。

## 4. Showcase 2 —— 带项目上下文的编码与代码评审

### 实际问题

通用编码 Agent 能写出语法正确的代码，却可能漏掉工作室约定、子系统边界、埋点要求、API 契约或更早的设计决策。通用代码评审有同样的短板：没有项目上下文时，它要么漏掉一条本地规则，要么报出一堆不相关的最佳实践。

### 知识库如何改变工作流

在规划与生成阶段，Agent 会检索项目专属的示例与约束，例如：

- 埋点要走的工作室 SDK 路径；
- 既定的子系统职责划分；
- 推荐的 API 与错误处理范式；
- 相关的设计决策与实现历史；
- 仓库评审指引与版本控制规则。

在评审阶段，专门的逻辑、质量、安全与性能评审者会先基于同一套知识基座，再对改动发表意见。稳定的指令可以同步进仓库本地的指引，而知识库只在改动确实需要时提供更深的证据。

![Agent 结合检索到的项目知识与仓库证据评审任务方案](assets/images/deepwiki/knowledge-backed-review-output.png)

*评审 Agent 检索项目知识、检视相关实现，并给出具体的必改项与验证指引。*

### 关键优化

最有效的改进不是加大 prompt。而是改善来源治理，并控制进入任务上下文的内容。DeepWiki 的默认结构提供了有用的起点，但工作室专属的知识结构、精心整理的本地地图与检索规则，才能让输出贴合真实的工程流程。

### 结果

代码生成与评审可以引用项目自身的标准、契约与示例。工作流仍然可复核，因为检索到的上下文都绑着项目证据，而人始终是接受生成代码或评审结论的最终权威。

## 5. Showcase 3 —— 为工作室专属流程定制业务 wiki

### 实际问题

每个工作室都有自己的业务词汇、内容结构、配置模型与日常流程。对设计师和内容团队来说，有用的入口很少是某个仓库模块或通用文档树。他们需要按玩法特性、竞技场、角色、战斗配置、剧情内容与相关资产这类概念来导航，并理解来自不同系统的信息如何归属到一起。

通用代码 wiki 不可能仅靠改目录就提供这种体验。业务模型、页面模板、来源映射、关系与问答边界，都必须反映客户真实的运作方式。

### 知识库如何改变工作流

团队与客户一起梳理 wiki 必须支撑的具体任务，然后围绕这些需求设计并实现一套面向业务的知识体验：

1. **对客户领域建模。** 定义工作室使用的导航、术语、实体与关系——例如特性模块、竞技场规则、角色记录、配置、剧情内容与资产。
2. **设计场景化页面。** 为用户需要放在一起的信息构建页面结构。一个角色页可以把档案数据、战斗与配置细节、剧情上下文、资源与源码引用合在一起，而不是把它们摊成一堆互不关联的文件。
3. **映射并转换项目数据。** 接入相关的已审批来源，把它们的原生结构转换成业务模型，同时保留验证所需的标识与来源关系。
4. **加入上下文问答。** 让用户能在当前业务页面内、或跨整个定制 wiki 提问，答案基于已装配的项目知识。
5. **用客户流程验证。** 拿真实任务检验信息结构与查询行为，在通用模型不适配的地方调整页面模板与数据映射。

![融合角色数据、配置、剧情资源与上下文问答的定制业务 wiki](assets/images/deepwiki/custom_wiki.png)

*这个定制角色页把业务数据与相关知识收进一个客户专属的结构里，页面旁即可进行上下文问答。*

### 结果

客户拿到的是一套按需构建的业务 wiki，而不是把章节改个名的通用代码 wiki。设计师与内容团队可以用自己的领域语言浏览知识，在一处查看相关信息，并站在当前业务实体的上下文里提问。同样的定制方法可以复用到其他工作室领域，但信息模型与交付形态取决于每家客户的实际需求。

## 6. 范围、边界与落地建议

### 当前能力

- 面向 P4、Git 与 SVN 代码库的结构化 wiki 生成与自然语言问答。
- 面向工程、设计、美术、QA 与运维知识的多来源接入。
- 面向 GamePilot AI 工作流的查询 API。
- 基于工作室需求、领域模型、页面模板与来源映射的定制业务 wiki。
- 自建部署与基于角色的内容访问控制。

### 当前边界

- 检索质量取决于来源质量、时效性、权限，以及工作室选择的知识结构。
- 聊天与单据历史里可能包含过时或非正式的决策；接入并不会把每句话都变成权威指导。
- 生成的答案必须暴露足够证据供用户核验；知识库不取代代码负责人、设计师或评审者。

### 建议的采用路径

先选一个项目和两个高价值场景：新人上手 + 一个日常研发流程。从代码库生成初始 DeepWiki，与工作室一起定义所需的业务结构与来源映射，只接入这两个场景必需的项目来源，并用真实问题衡量检索质量。等归属、权限、时效性与证据质量都稳定可靠之后，再扩展到更多来源与角色。
