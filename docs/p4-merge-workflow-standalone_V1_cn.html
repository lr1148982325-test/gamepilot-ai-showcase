P4 合并工作流

面向百万级文件 Perforce 合并的分阶段、规格驱动能力

长线运营的游戏工作室如果维护着一款 Unity 产品的定制下游分支，就需要周期性吸收上游 dump。这份 dump 可能是供应商快照、本地化分支，或另一个团队的主线。下游分支上已经带着版本号、热更地址、商店与计费规则、平台 SDK，以及数年积累的本地玩法。把这样一棵树用一次 p4 integrate 合进现网分支不叫合并——那是一场等着发生的事故。

P4 合并工作流把这场事故变成一个可复用的 GamePilot skill：识别真实的 stream 拓扑、按内容摘要（而非全量 reconcile）同步 dump、把现网分支继承到一个临时合并 stream、把剩余工作拆成路径互不重叠的待提交 changelist，并通过规格、Agent 和一位仍然掌握每次提交权的人来逐波解决。

本 Showcase 聚焦于传统 Perforce 路径扛不住的问题、可复用的架构，以及在一个百万级文件 Unity depot 上已被验证的部分。

1. 背景：合并是必需的，但传统路径无法扩展

Unity 长线运营 depot 体量大、二进制多，且语义上被切分。上游与下游通常是同一主线下的兄弟开发 stream——它们之间没有父子 integrate 记录（credit）——因此这次变更无法「沿着 stream 图」合并，必须分阶段进行。

工作所在 实际问题 流程影响
百万级文件上游快照 p4 reconcile 要对工作区里每个文件与服务器做一次 stat 本该几小时的同步被拉长到几天；中断就得重来
下游现网分支（Staging-launch 等） 发布配置、CDN/补丁地址、商店、CI 与平台端点都是下游独有 天真地 accept-theirs 会把构建指向错误的服务器，或丢掉计费规则
Stream 拓扑 base/sync 与现网分支是兄弟关系，不是父子 直接 integrate 进现网既不安全，历史上也会出现 credit 混乱
冲突面 代码、Prefab、.meta、asmdef、表格与美术资源同时冲突 一个巨大的待提交 CL 无法被评审、编译，也交不到第二个人手上
Agent / 工程师上下文 p4 integrate -n 与 p4 resolve -n 会吐出几万行输出 直接读原始输出的模型，窗口全耗在噪声上，仍然无法安全提交

把 Agent 接到 p4 上、却不给工作流，并不能解决问题。Agent 要么卡在命令输出上，要么自动合并那些必须保持下游状态的文件，要么打开路径重叠的文件——而 Perforce 拒绝把同一路径放在两个待提交 changelist 里。因此目标不是「一个会跑 Perforce 的 LLM」，而是一项可复用的工程能力，用来回答一个更窄的问题：工作室如何持续地把上游 dump 吸收进定制的现网分支，既不丢失下游语义，又不逼一个人在一个下午内解决上百万个文件？

2. 可复用架构

这项能力是一个 GamePilot skill 加上一小组本地确定性辅助脚本。skill 是编排层。脚本从不提交。LLM 从不写 depot。人始终是验收权威。

组件 职责
Perforce streams 唯一数据源。上游快照、sync 镜像、临时合并分支、现网目标
GamePilot skill 识别拓扑、编排五个阶段、压缩命令输出、应用规格、记录审计
sync-from-upstream.py 针对本地 dump 生成基于摘要的 add/edit/delete 计划。带缓存、可续跑、不提交
analyze_asmdef_topology.py 只读的 Unity 程序集依赖图，用于给波次排序
summarize_diff_for_batching.py 把 p4 diff -se 压缩成 Agent 真正能用的模块/类型/目录计数
三层合并规格 核心红线、本次合并的运行时规则、工作室专属模块策略
.p4-merge/ 审计 用于恢复的精简 state-summary.md、按 CL 追加的日志、人类可读的 CL 地图
人 确认无法判定的文件，并提交每一个 changelist
LLM 只做规划与逐文件判断。可自建或云端托管；不在 depot 写入路径上

这种切分让工作室可以渐进采用。团队可以先只对一个 dump 做摘要同步进 sync，下次导入时再加临时合并分支，等冲突面大到一个人扛不住时，再开启波次规划与规格驱动的 resolve。

3. Showcase 1 —— 用摘要同步取代全树 reconcile

实际问题

第二阶段要做的就是「让下游 sync stream 与这份上游快照完全一致」。传统 Perforce 的做法是对 client 跑 p4 reconcile。在百万级文件的 Unity 树上，这意味着每个文件一次服务器往返、没有像样的断点续跑，而且整个运行期间工作区看起来都是脏的。工作室要么干等，要么挑着 cherry-pick，然后慢慢与上游脱节。

工作流如何改变它

  1. Agent 绑定一个专用的 sync client，并在任何变更命令之前记录 p4 info / p4 opened。
  2. sync-from-upstream.py 把 p4 files / p4 fstat 批量拉进本地摘要缓存，扫描快照算 MD5，并写出 add / edit / delete 计划。
  3. 只有摘要真正变化的文件才被 open。未变化的文件完全跳过。
  4. 缓存按服务器、用户、depot 根与 head changelist 做键。中断的运行从最后完成的批次继续。
  5. 脚本停在「已 open 文件」这一步。由人检查 p4 opened / p4 diff -se 并提交。

在百万级文件 depot 上实测，这比 reconcile 快约一个数量级，因为昂贵的工作从「逐文件服务器 stat」变成了「本地摘要比对」。

结果

sync 成为一个忠实、可审计的 dump 镜像，而不需要一个长达数天的 reconcile 窗口。现网分支仍然未被触碰。这正是重点：导入与合并是两件事，把它们混在一起，就是下游端点被覆盖的原因。

4. Showcase 2 —— 波次规划与四层 resolve 漏斗

实际问题

sync 跟上之后，剩下的工作就是把它与现网分支合并。一次性 integrate 会产出一个没人能编译、评审或恢复的待提交 CL。Unity 让顺序问题更糟：Prefab 比脚本先落地会出现缺失组件；程序集比依赖先落地就编译不过；.meta 与主文件分家会变成无法提交的状态。

兄弟 stream 的历史还带来第二个陷阱。一次先前中止的合并可能留下陈旧的 integrate credit，于是普通 p4 integrate 报告「所有版本已整合」，而 p4 diff2 仍显示真实差异。

工作流如何改变它

skill 从不直接 integrate 进现网。它先把现网复制到一个临时合并分支，使下游独有工作成为基线，然后分波次把 sync integrate 进那个临时分支。

阶段 4A（规划一次）。 Agent 用 asmdef 拓扑、目录结构、GUID 引用、配置配对与项目规格来起草波次。每个波次通过 p4 integrate -c 拿到自己编号的待提交 changelist。路径被要求互不重叠。文件数与改动量预算在文件被 open 之前就用 integrate -n 检查，因此过大的代码波次在规划阶段就被拆分，而不是拖到 resolve 时。陈旧 credit 用带 -f 与不带 -f 两种方式探测；删除用 -Ds 覆盖；残留文件被扫进一次针对性的清理 CL，而绝不用全分支 -f。

阶段 4B（执行一个 CL）。 波次负责人跑一个漏斗：

  1. p4 resolve -am 处理不重叠的编辑。
  2. 三层规格批量 accept theirs 或 yours（-at / -ay）。
  3. Agent 阅读剩余文本文件（约 500 行以内）的 diff。
  4. 二进制、超大 diff 与无法判定的文件，连同一段摘录和建议一起交给人。

核心规格的红线不可协商：除非人显式覆盖，下游的版本/渠道/热更/CDN/商店/CI 一律保留在目标侧。上游协同进行的重构作为一个整体接受。一个 .asmdef 如果上游新增了引用、但同时承载下游独有程序集，则采用并集合并，而不是盲目照单全收。

每个决策都追加到该波次的 CL 日志。全局 state-summary.md 是 Agent 唯一原地重写的文件，因此崩溃的会话靠读几十行就能恢复，而不必翻一份巨大的 transcript。

结果

一次百万级文件的 integrate，变成一列可评审的 changelist：各有明确负责人、明确路径范围，以及一条符合 Unity 真实依赖顺序的编译故事。单个代码波次之后出现中间态编译失败被视为正常，而不是回滚整次合并的理由。

5. Showcase 3 —— 一套流水线支撑 1..N 个人，靠 shelve 交接

实际问题

这次合并对一个人太大，又耦合到不能「各人 integrate 自己的目录」。Perforce 里编号的待提交 changelist 绑定在创建它的 client 上，无法改派。共用工作区更糟：机器不在一处，open 的文件会撞车。

工作流如何改变它

只有一条流水线。人数变化只改变谁来执行 4B，而不改变波次如何规划。

  • 一个人： 协调者是唯一执行者。resolve 与提交都发生在协调者 client 上。不使用 shelve。
  • N 个人： 4A 仍然在协调者 client 上建好每一个待提交 CL，然后对每个波次 p4 shelve。负责人把波次 unshelve 到自己的 client 上、本地 resolve、再 shelve 回来。协调者 unshelve 回收结果，并且是唯一提交者。

人员名单来自项目开发者清单外加手工覆盖，因此美术波次可以给美术、表格波次给设计、代码波次给程序，而不必发明第二套流程。因为 4A 已经让路径范围互不重叠，并行 resolve 在文件层面是安全的，不需要加锁协议。

人类可读的 cl-dependencies.html 查看器是模板的一份静态副本；只有很小的 cl-dependencies-data.js 会在状态变化时重写。人们可以直接用浏览器打开这张地图，不需要本地起服务。

结果

最贵的脑力活——「哪些文件属于这个波次，它们是否重叠？」——只做一次。执行可以跨机器扇出，而不必分叉计划、不必共用 client，也不需要除协调者以外的任何人向临时分支提交。

6. 范围、边界与落地建议

当前能力

  • 拓扑优先的准备工作：现网/冻结 stream 用 p4 streams 与最新 CL 日期检测，而不是照抄一份过期示例。
  • 基于摘要的快照导入到 sync stream，可续跑，不自动提交。
  • 临时合并分支先继承现网，再吸收 sync。
  • 模块优先的波次规划，含 Unity asmdef 顺序、CL 体量预算、删除覆盖与陈旧 credit 处理。
  • 由核心、运行时与项目三层规格引导的四层 resolve。
  • 支持中断续跑与多人追加式 CL 日志的精简审计。
  • 当多个 client 需要执行波次时的 shelve 交接。
  • 已在 NIKKE a2-frontend depot 上验证：上游 //unity/qa-* 快照进入 //a2-frontend/base/sync，再经临时分支流向 //a2-frontend/version/Staging-launch。

当前边界

  • skill 不会自动提交。准备、检查与记录是自动的；提交是人的动作，除非用户显式下令。
  • 它不会把上游合并进现网分支。那条路径正是本工作流要防止的失败模式。
  • 在大型 client 上跑大范围 p4 reconcile 属于禁止策略。摘要同步才是导入工具。
  • 检索与 resolve 质量取决于规格质量。缺少项目规格时核心红线仍然生效，但工作室专属模块（例如「商店完全属于下游」）必须写下来。
  • Agent 按设计只看压缩后的命令输出。它不会去读两万行的 resolve -n dump。
  • 禁止使用 p4 obliterate。处理坏波次的方式是 revert 或用反向 CL 撤销。
  • 命令假设 Windows Perforce 工作区与 PowerShell。该 skill 不是一个跨 OS 的 p4 封装。

建议的采用路径

从一份 dump 和两件事开始：(1) 用摘要同步把它同步到专用的 sync stream；(2) 在一次性临时分支上跑 4A 的 dry-run，直到波次预算与残留覆盖都诚实为止。从前十个已确认的 resolve 决策里写出第一份运行时规格。只为那些反复违反通用规则的模块追加项目规格。等单个负责人干净地提交过几个波次之后，再扩展到多人 shelve——协同成本是真实存在的，只有计划稳定之后它才划算。

可复用的内核是：分阶段拓扑、摘要导入、路径互斥的波次、规格漏斗与精简审计。NIKKE 的文件清单是项目包，不是产品本身。
