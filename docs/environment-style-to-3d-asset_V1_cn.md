# 概念图风格迁移生成 3D 资产：在无限画布上从概念板走到可交付的 .glb

环境概念图与可交付的 3D 资产之间隔着三道鸿沟，而它们都与模型质量无关。概念图是**透视**的——它为单一机位构图、营造氛围、布置光照；生产资产必须**正交**、无歧义、且是单一主体。概念图表现的是**一片聚落**，而 DCC 工具导入的是**一个网格**。概念图承载的是**风格意图**，网格承载的是**几何事实**。靠手工去弥合这些鸿沟——重绘概念板、补画转面图、从零建模——正是工时消耗的地方。

这条工作流把它们端到端地打通：输入两张上传图片（一张内容板、一张风格参考），输出两个带贴图的 `.glb`，全程走一张 20 节点的八阶段图。

| 项目事实 | 当前证据 |
| --- | --- |
| 工作室协作 | Yongxing-Spirits — |
| 画布 | Inficanvas，通过 GamePilot 门户进入；工作流保存为 `inficanvas-workflow` v1 |
| 图规模 | 20 个节点——16 个 Image（其中 2 个为上传节点）、2 个 Text、2 个 3D Asset；2 个分组 |
| 图片模型 | `gpt-image-2` × 5，`gemini-3.1-flash-image` × 9 |
| 3D 模型 | `tripo3d/v3.1-20260211`，`multiview-to-3d`；6 万面与 4 万面；`meshQuality: ultra`、`textureQuality: ultra`、开启 PBR |

## 1. 生产问题：三道鸿沟，而不是一次建模

最朴素的说法是"用概念图生成 3D 资产"。这句话里其实藏着三个相互独立的失败点：

1. **投影。** 透视概念板的边线是收敛的，存在近大远小的透视缩短。而多视图转 3D 的模型期望的是平行投影。直接把原始概念图喂进去，重建出来的楼是歪的。
2. **主体范围。** 概念板画的是一个场景，而网格必须是一个东西。整片聚落必须先被拆解，并且在推断任何几何之前，先单独隔离出一个候选主体。
3. **风格与结构。** 重绘概念板时往往会连带改写它的内容——塔楼变成了另一座塔楼。而重绘后的板子是后续所有环节的输入，这里的偏差会被永久放大。

这条工作流为每道鸿沟各设一个专门的阶段，而不是指望一次生成同时解决三个问题。

## 2. Showcase A — 重绘板子但不改写建筑

### 背景与问题

第一步是风格迁移：拿一张滨水聚落的概念图，按目标美术方向重新绘制。它的失效模式人所共知——一个可以自由发挥的重绘模型会"顺手优化"主体。塔楼多出几层、桥的跨度变了、剪影整体漂移。由于重绘后的板子是后续所有阶段的输入，这种漂移是永久性的。

### 迭代与优化

工作流把这个问题拆成两个结构化解析节点和一个被严格约束的生成节点。

在上传与迁移之间放着两个 **Text 节点**。它们只存放文本、不做生成，也不消耗算力，各自带一段 `textGenerationPrompt`，用来定义严格的输出契约：

- **Text1（内容）** 把板子拆解成六个固定维度——主体、场景、构图、视角、几何与线条、关键细节——并要求最终输出一段 60–120 字的描述性段落，其中**零色彩词、零风格词、零媒介词**。
- **Text2（风格）** 把风格参考拆解成七个维度——媒介、色板（给出显式 hex 值，如 `#D96B5F`、`#2F6F73`）、光照语言、笔触与材质、氛围、标志性元素，以及一行风格标签——并要求输出一段 60–100 字的段落，其中**零具体物体名词**。

两份契约互为镜像：一份描述场景**是什么**，同时禁用风格语汇；另一份描述它**看起来如何**，同时禁用物体语汇。这种对立保证了内容与风格在重新组合之前不会互相污染。

生成节点本身只带一段 72 字的中文提示词，而整套重绘策略都在里面：

> 保留参考原图的构图、主体身份、相机角度与空间布局；仅应用参考风格图的美术风格、配色、光影与质感。不要改变画面中出现的物体——只改变它们的呈现方式

> *Preserve the source image's composition, subject identity, camera angle and spatial layout; apply only the reference's art style, palette, lighting and material. Do not change the objects present in the frame — change only how they are presented.*

### 最终效果

这条约束干净且可复用：它把风格的权限授予**呈现方式**，同时否定它对**存在与否**的处置权。对一条后续阶段要测量几何的管线来说，这个区分就是全部意义所在。

## 3. Showcase B — 把聚落拆解成可提取的单个资产

### 背景与问题

重绘后的板子仍然是一个场景。在推断任何几何之前，必须先从中选出一样东西。传统做法是用眼睛挑、用手裁，这通常意味着要反复猜测哪些元素能被干净地重建。

### 迭代与优化

工作流把拆解变成了一个显式的生成阶段。**Image1**（2K）使用一条 kit-bash / 拆解图提示词，把板子炸开成中性影棚背景上的一个个独立资产元素，并要求版面按三个带标签的分组组织：

- **核心结构**——主楼被拆成模块化的墙面分段或外壳。
- **模块化道具**——更小的功能性细节：窗、门、机械部件、硬表面构件。
- **环境 / 植被**——有机元素、地面散布物、岩石、背景装饰，各自拆成独立的资产节点。

提示词还要求每个资产继承原图完全一致的贴图、PBR 属性、粗糙度与做旧程度——这正是让这张拆解图能被当作建模参考、而不只是一张插画的原因。

随后两个提取节点从这张图上各取一个单体，**在同一父节点下并行**运行：

- **Image2** 提取一个建筑单元。它的提示词由九条负向约束主导：不要合并多个资产、不要拼接来自不同建筑的部件、不要增加输入中不存在的楼层、屋顶、平台、栏杆或装饰、不要生成一组物体。
- **Image4** 提取一个非建筑结构——桥、平台、栈道、栏杆——并配一套平行的禁令。

两条提示词用同样的话陈述意图：*这是"提取一个已有的单元"，而不是重新设计它。* 两者也都规定了交付格式：一个单元、完整、居中、四周留白、四分之三视角、浅色背景、自然的接触阴影。

### 最终效果

提取出一个建筑单元和一个非建筑结构，就为下一阶段提供了两个互不相干的候选，各自带有适合其重建条件的剪影特征。

这里有一条使用规则很关键：**用于 3D 输入的多视图图不携带任何文字标签和比例立方体。** 喂给 3D 生成的那些视图图，其提示词都明确以 生成结果不要有任何文字和3D 立方体 收尾——标注会干扰重建。

*拆解图把一个场景变成了一份目录。按结构 / 道具 / 环境分组，正是让下一步提取变成"挑选"而不是"搜索"的原因。*

## 4. Showcase C — 正交校正、切图与 3D 生成

### 背景与问题

提取出的单元仍然是一张四分之三视角的透视渲染图，而多视图转 3D 需要平行投影。这个校正必须在生成之前完成，而且必须保持材质连续性——一张在视图之间改变了砖纹的转面图，会产出贴图错位的网格。

### 迭代与优化

生成两张正交图，一条提取分支一张：

- **Image3**（承接 Image2 的建筑单元）规定三视图横向排布：正面、左侧、背面。
- **Image5**（承接 Image4 的结构）规定 2×2 网格，并列出四个视图：正面、左侧、背面、顶视。

两条提示词都以同一个要求开头：输入的斜透视**必须**被校正为无畸变、适合 3D 建模的平行投影；两者都要求逐视图的 PBR 一致性、贴图完全一致，并保留原图中可见的特定做旧、苔藓或锈迹细节。

随后这些图被切成单个视图。切图是一个**在画布之外手工完成的步骤**：每个视图被裁切后作为独立节点上传回来。视图角色并不附着在图片本身上——它是在 3D 节点上、通过 `threeDReferenceViews` 字典指派的，该字典把每个切片绑定到某个相机角色（`front`、`left`、`back`、`right`、`top`）。因此，"生成多视图图"与"给视图标注"是两个解耦的操作：某个切片可以重新裁切或替换，而无需改动任何提示词。

两个 3D 节点都运行 `tripo3d/v3.1-20260211` 的 `multiview-to-3d` 模式，`meshQuality: ultra`、`textureQuality: ultra`、开启 PBR、关闭部件生成。

### 最终效果

产出两个 `.glb` 文件：

| 资产 | 输入切片 | 面数 | 输出 |
| --- | --- | --- | --- |
| Asset3D1 | 3（9:16，分组 `3x1`） | 60,000 | `model_1787123072061_s3dia0836.glb` |
| Asset3D2 | 4（16:9，分组 `2x2`） | 40,000 | `model_1787123138060_k3ph94pl1.glb` |

面数是按资产分别设定的，而不是继承某个全局默认值——建筑单元拿到的预算比桥梁结构多出 50%。

## 5. 它解决了什么——以及没解决什么

**解决了什么。** §1 中的三道鸿沟各由一个专门阶段处理，整条链路跑到了一个真正可交付的产物。风格被迁移而没有结构漂移；场景被拆成目录，再拆成单个资产；透视在推断几何之前被校正为平行投影。最终输出是指定面数预算下带 PBR 贴图的 `.glb`——一个能在 DCC 工具里直接打开的文件。

其中两点设计可以推广到这次运行之外：

- **内容与风格在相反的约束下被解析**，然后才重新组合。两份契约各自禁用对方的语汇，这比事后再去过滤要便宜得多。
- **视图角色是消费侧的元数据。** 切片之间始终可互换，重新标注某个视图的代价为零。

**没解决什么。**

- **整条管线并未完全自动化。** 切图是对每个视图手工裁切再上传；目前没有能自动拆分网格的节点。
- **没有任何校验。** 3D 节点只报告 `success`。没有拓扑检查、没有水密性闸门、没有比例检查、没有 UV 检查，也没有网格与原始剪影之间的比对。一个技术上合法的网格仍然可能是错的建筑——验收前请在 DCC 工具里检视 `.glb`。
- **面数是输入值，不是实测值。** 60,000 与 40,000 是申请的预算，实际网格密度请在导入时核实。
- **单次运行的证据。** 所示结果来自一张概念板。相对手工基线，验收率与节省的美术工时尚未测量。

## 6. 端到端流程一览

| 阶段 | 输入 | 操作 | 输出 |
| --- | --- | --- | --- |
| 1. 风格感知解析 | 内容板 + 风格参考 | 两份文本契约按相反语汇规则拆解内容（6 个维度）与风格（7 个维度） | 结构化的内容与风格描述 |
| 2. 风格迁移 | 解析描述 + 板子 | 受限重绘：保留构图、主体身份、机位；只改变呈现方式 | 重绘后的板子 |
| 3. Kit-bash 拆解 | 重绘后的板子 | 生成按三个带标签分组（结构 / 道具 / 环境）组织的拆解图 | 资产目录 |
| 4. 单体资产提取 | 拆解图 | 在严格负向约束下并行执行两次提取 | 一个建筑单元、一个非建筑结构 |
| 5. 正交校正 | 提取出的单元 | 透视 → 平行投影，并保证逐视图的材质连续性 | 三视图与四视图正交图 |
| 6. 视图切分与角色指派 | 正交图 | 手工裁切并上传；在 3D 节点上通过 `threeDReferenceViews` 绑定相机角色 | 带标注的单个视图 |
| 7. 多视图转 3D | 带标注的视图 | `tripo3d` multiview-to-3d，网格/贴图质量 ultra，开启 PBR | 两个带贴图的 `.glb` 资产 |

## 7. 可复用能力以及如何跑起来

可复用的能力不是任何一个模型，而是对一份欠定输入所做的**分阶段拆解**：

1. 在**相反语汇约束**下对内容与风格做结构化解析。
2. 由显式的"保留 / 改变"二分来划定风格迁移的边界。
3. 场景 → kit-bash 目录 → 单体资产提取。
4. 透视 → 正交校正，并保证逐视图的材质连续性。
5. 消费侧指派视图角色，喂给多视图转 3D。
6. 把逐资产的面数预算与 PBR / 贴图质量作为显式参数。

要在一张新的概念板上跑起来：

1. 上传内容板与风格参考；两份解析契约和保留/改变的迁移提示词保持原样。
2. 跑 kit-bash 拆解，然后挑出与你主体类型匹配的两条提取分支；只有当你的主体既不是建筑也不是结构时，才需要调整负向约束。
3. 生成正交图，裁切每个视图，上传切片，并在 3D 节点上绑定相机角色。
4. 逐资产设置面数预算，运行多视图转 3D，并在验收前用 DCC 工具检视 `.glb`。

现有证据足以支撑一次受控的工作室试点——衡量指标是从概念板到验收资产所花的美术工时，基线是手工重绘加建模的流程。它还不足以证明成本下降，因为它只记录了一次运行，既没有基线，也没有可度量的产出。
